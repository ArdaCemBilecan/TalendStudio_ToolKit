# Changelog

All notable changes. The model's `schema_version` is bumped when the JSON shape changes.

## 0.9.0

- **Portable bundle for customers with many users and servers** (`tools/build_portable.py`, see
  [docs/deployment.md](docs/deployment.md)): one folder (`dist/tmt/`) with an embedded Python, the dependencies and `tmt`. Zip it,
  unzip it on a server and double-click `Start tmt.bat`; no installation, no administrator rights, offline.
- `tmt ui [WORKSPACE]`: open a workspace straight away (drag a folder onto `Start tmt.bat`). Without it the page
  uses the last workspace, or finds the user's own one (`$TMT_WORKSPACE`, `~/workspace`, `~/Talend_WS`, ...).
- `tmt ui` listens on port 8765 by default (so the browser remembers the last workspace) and falls back to a free
  port when it is taken, for example by another user on the same server.

## 0.8.0

- **A new look: the explorer is laid out like a Talend Studio perspective.** Repository tree (Job Designs with master
  jobs and their sub-jobs, Db Connections), editor tabs, a Designer-style canvas, Sources/Targets/Connections lists
  and a Properties panel. Click a connection to highlight the jobs that use it. Light and dark follow the system.
- `masters` rows (in `/api/inspect` and `/api/explore`) carry their direct `children`.

## 0.7.0

**The project is now built around the dependency graph.** Removed: `tmt report`, `tmt dbt`, `tmt all`,
`tmt explain` (and the dbt generator, the explainer plugin point and the HTML/Markdown report); the UI's "More tools"
and its command runner. Their code is in git history of your own backup only; nothing else depended on them.

- `tmt ui` is read-only: no routes that run commands, write files or serve files. *Save as SVG* exports the graph.
- `tmt graph --master JOB` keeps one master job and every job it starts, and prints jobs, sources, targets and
  database connections (`10x ODS_DB`) on stderr.
- `tmt parsers` lists parsers only. The `jinja2` and `duckdb` dependencies are gone.

## 0.6.0

- **`tmt ui` is now a dependency explorer.** Choose a workspace, optionally a **master job**, and see its workflow
  as the lineage graph. Hovering a job or table shows its sources, targets and connections; the summary gives the
  distinct sources and targets of the workflow and the database connections by name (`10x ODS_DB`, `2x AKY_DB`).
  The earlier action cards moved under *More tools*.
- **Database connections in the model** (`schema_version` 0.4): every database component carries the Studio
  metadata connection it uses (`connection`: name, kind `repository` / `inferred` / `built_in` / `shared` /
  `unresolved`). Resolved by repository id (also across sibling projects), through shared `t<DB>Connection`
  components, and, flagged as an inference, from the context variables Studio names after the connection.
- `samples/talend_demo`: a synthetic project (master jobs, two metadata connections) that reproduces the example above.
  Generated by `tools/generate_demo.py`.
- Interactive SVG (`data-node` attributes, keyboard focus) for the explorer; the exported SVG is unchanged.

## 0.5.0

- **`tmt ui`: a point-and-click interface.** A local web page (standard library only, no extra install) where you
  pick a folder (with a folder browser), pick an action, set options and press Run. It shows the exact command,
  the result in words, the files created (open or preview), and draws the lineage graph in place. See
  [docs/ui.md](docs/ui.md).
- Security of the interface: loopback only, private random token, `Host`/`Origin` checks, whitelisted actions run as
  argument lists (never a shell), validated values bound to their flag, files served only from a run's output
  folder under a strict Content-Security-Policy. Covered by tests that break each defence on purpose.
- `tmt graph --format svg`: the lineage graph as a self-contained SVG (no scripts, no external assets, light and
  dark). Also used by the interface.
- `python -m tmt` works like the `tmt` command.

## 0.4.1

Found by scanning a real Talend workspace (36 jobs, three projects); none of it showed up on the synthetic samples.

- **Fixed: same-named jobs overwrote each other.** A project cloned from another (DEV to PROD) repeats every job
  name *and* every Studio id. Output files were named `<job>.json`, so one job silently replaced another, and the
  lineage graph merged them. Jobs now have a unique `Job.key` (the plain name when unique, else `name@project`,
  `name@project/folder` or `name@path`); files, graph nodes, reports, dbt models and `explain` use it, and
  `--job` / `--focus` accept a key or an unambiguous name. `schema_version` 0.3 (`key`, `repo_id`, `project`).
- **Fixed: `tRunJob` children are resolved by `(project, id)`**, the way Studio writes the reference
  (`DEV:_abc`), not by name or bare id. An orchestrator in PROD that calls DEV's jobs now resolves to DEV's.
  An ambiguous name is reported, never guessed.
- **Fixed: silent loss for migration placeholders.** Queries such as `"$Stage.READER.Query"` and default labels such
  as `"Output for table"` produced no tables and **no warning**. They now raise `placeholder_value`, count towards
  the complexity score, and make the dbt generator refuse the job.
- A statement that parses but is not a recognised statement type is flagged instead of accepted as "no tables".
- `tmt explain`: unanalysable queries are described plainly; steps use natural order (`_2` before `_10`).
- Scan summary: the job column no longer breaks names, and its width adapts to the terminal.

## 0.4.0

- Plugin interface: parsers (`tmt.parsers` entry points) and explainers (`tmt.explainers`), discovered with
  validation; a broken plugin is skipped with a warning.
- `tmt.testing.contract.ParserContract` and `validate_job()`: contract tests any parser must pass. Run against the
  Talend parser and a dummy second parser.
- `tmt explain`: plain-language job descriptions. Built-in offline explainer; no LLM bundled; custom Java source is
  withheld unless `--include-code`.
- `tmt parsers`, `--parser`, `-q`, documented exit codes, `error:`/`hint:` messages instead of stack traces.
- Docs: `architecture.md`, `adding_a_parser.md`, `explain_hook.md`; documentation consistency tests.
- Fixed: file discovery was hard-wired to Talend's `*.item`, so another tool's files were never seen; output
  write errors (unwritable or over-long `--out`) crashed with a traceback; "(s)" placeholders in user-facing text.
- `Job.source_tool` is now a free string.

## 0.3.0

- `tmt dbt`: conservative dbt skeleton (`models/*.sql`, `sources.yml`, `schema.yml`) for Snowflake. Eligibility
  rules, `-- TODO(manual)` for untranslatable column mappings, `_eligibility.json` with reasons.
- Java-to-SQL expression translator (parsed, never executed; unsupported constructs are rejected, not guessed).
- Generated models are parsed with sqlglot and executed on sample rows in the test suite (DuckDB).
- Model: aggregate/unique/sort settings, tMap join keys with lookup column and operator, `matching_mode`.
  `schema_version` 0.2.
- Two more sample jobs (`job_join_aggregate`, `job_union_filter`).

## 0.2.0

- Complexity scoring (weights and thresholds in `config.yaml`), each point listed as a reason; custom Java forces
  "hard".
- `tmt report`: Markdown and a single self-contained HTML file (dark mode, phone width, no external assets).
- `tmt all`.

## 0.1.0

- Talend 8.0.1 parser, intermediate model (pydantic, `extra="forbid"`), per-job JSON output.
- Lineage graph (Mermaid, DOT, JSON), suggested migration order, cycle detection.
- `tmt scan`, `tmt graph`; golden-file, fuzz and security (XXE, entity bomb) tests.
- Synthetic sample jobs and their generator; `docs/talend_format_notes.md`.
